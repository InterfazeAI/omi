# Measurements

Raw evidence for the battery claims made elsewhere in this tree, plus the scripts that turn it back
into those numbers.

**This directory holds data, not conclusions.** The conclusions live in
[`devkit/DEBUGGING.md`](../../../devkit/DEBUGGING.md) — traps 14 (the gauge), 18 (the flat cell that
erased a filesystem), 19 (the boot gate) and 20 (the guard that never rolled). Anything asserting
*why* belongs there; anything asserting *what was observed* belongs here. Keeping both in one place
is how the two drift apart.

Every figure quoted in those traps is reproducible from what is in this directory. If a number in
the docs cannot be regenerated by one of these scripts, treat the number as suspect.

## Data

`logs/` holds three `battery.py --watch` runs covering one full discharge of an Omi DevKit 2 —
recording continuously to SD with BLE advertising, no USB, one cell, one temperature.

| File | Span | Notes |
|---|---|---|
| `drain-2026-08-23-overnight.log` | 4,020 → 3,813 mV, 8.0 h | the upper region, ~23 mV/h |
| `drain-2026-08-23-to-empty.log` | the plateau and into the knee | longest run |
| `drain-2026-08-24-to-empty.log` | tail, ends 3,455 mV | board still running at the last sample |

1,333 samples total. The gaps between runs are logger downtime, not the board being off, so elapsed
wall time is continuous across them.

**The one thing these logs do not contain is the death.** Logging stopped at 3,455 mV with the board
alive, and the cell was flat 6.5 h later. Everything about the bottom of the curve is bounded by
that window, which is why the analysis reports the cutoff as a range (3,330–3,390 mV) rather than a
value.

## Analysis

Run these with the `sd_sync` virtualenv: `../sd_sync/.venv/bin/python <script>`. Derived output
(JSON, PNG) goes to `out/`, which is not committed — it is reproducible from the logs beside it.

| Script | Produces |
|---|---|
| `stitch_and_fit.py` | joins the three runs into one timeline, fits mV/h per region, bounds the cutoff. Writes `out/soc_curve.json`; run this first. |
| `chart_data.py` | reads that JSON and derives percent-of-runtime-remaining per voltage — the fit `battery_states[]` was rebuilt from. |
| `estimate_life.py` | least-squares discharge rate over several windows and a projection to a target voltage. |
| `plot_drain.py` | the whole discharge on one axis. Needs `matplotlib`. |

Rates come from least-squares fits over windows, never from differencing two readings: single
samples jitter about ±40 mV, which on the plateau is worth more than three hours of real discharge.

## `gauge_smoothing_sim.c`

Chooses the reported-percentage filter by measuring candidates instead of arguing about them.
Replays the real gauge path — guard mean, second-stage filter, monotone hold, and the integer
arithmetic of `battery_get_percentage()` including its truncating cast — against a cell draining at
the measured 19 mV/h with the measured ±40 mV jitter.

```
cc -o out/gauge_smoothing_sim gauge_smoothing_sim.c && ./out/gauge_smoothing_sim
```

It reports two numbers per configuration, and both are load-bearing: **reversals** (direction changes
in the published series, which should be zero for a monotonically draining cell) and **max lag**
(worst deviation from truth, which is what rules out the degenerate filter that scores zero
reversals by never moving). This is what established that a hysteresis band on the guard's mean —
the obvious first fix, and the one that was written first — still reverses 361 times, and that
`median of 32 + monotone` reaches zero while holding lag at 3 points. See trap 21.

Same caveat as below: it replicates the algorithm rather than executing the firmware's own code, so
it is recorded evidence for a decision, not a regression test, and nothing runs it.

## `guard_window_sim.c`

Replays `battery_guard()`'s ring indexing and strike logic on the host, once as shipped and once
fixed, against a cell ramped 4,100 → 3,300 mV. It is what established that the shipped
`window[filled % BATT_WINDOW]` could not fire the shutdown *at any voltage* rather than merely
biasing it — see trap 20.

```
cc -o out/guard_window_sim guard_window_sim.c && ./out/guard_window_sim
```

**This is recorded evidence for one finding, not a regression test, and nothing runs it.** It
replicates the algorithm rather than executing the firmware's own code, so it cannot fail when
`main.c` changes. A real guard would mean extracting the ring index behind a seam both the firmware
and a host test compile, and registering it in `.github/checks-manifest.yaml` — until that exists,
this bug class is uncovered.

## `reports/`

Archived snapshots of the two Cursor canvases written from this data — the discharge curve, and the
end-to-end battery flow with every threshold and percentage. They render inside Cursor from
`~/.cursor/projects/<workspace>/canvases/`; the copies here are for version history and are inert
outside it. **They are snapshots, so they will drift** — the logs and scripts above are the source
of truth, and `DEBUGGING.md` owns the prose.
